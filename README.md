# 💡 SvitloBot Monitor

Точне визначення наявності світла для [Світлобота](https://svitlobot.in.ua), яке **не плутає відключення світла з відключенням інтернету**.

## Як це працює

Звичайна схема — ESP32 сам пінгує Світлобот. Якщо вдома зник інтернет, пінги припиняються, і Світлобот помилково повідомляє «світла немає».

Тут перевірку робить окремий сервер (VPS) ззовні:

```
   VPS (Docker)                          Дім
 ┌─────────────────┐   HTTP :порт   ┌────────────┐      ┌──────────────┐
 │ SvitloBot       │ ─────────────► │  Роутер    │ ───► │ ESP32        │
 │ Monitor         │   ICMP / TCP   │  (на ДБЖ)  │      │ (без ДБЖ)    │
 │                 │ ─────────────► │            │      └──────────────┘
 └────────┬────────┘                └────────────┘
          │ channelPing (коли світло є)
          ▼
   API Світлобота ──► Telegram-канал
```

| Сторінка ESP32 | Пінг роутера | Стан |
|---|---|---|
| ✔ відповідає | будь-який | 🟢 **Світло є** — сервер пінгує Світлобот |
| ✖ не відповідає | ✔ відповідає | 🔴 **Світла немає** — пінги припиняються |
| ✖ не відповідає | ✖ не відповідає | 🟡 **Невідомо** — зник інтернет; за замовчуванням зберігається останній відомий стан, у канал іде тихе повідомлення |

> **Важливо:** схема працює, лише якщо **роутер живиться від ДБЖ**, а **ESP32 — напряму від мережі** (без ДБЖ та павербанка). Інакше при відключенні світла зникне і пінг, і стан буде «невідомо».

## Що потрібно

- Плата ESP32 (класична, напр. ESP32 DevKit / WROOM-32) і кабель USB з передачею даних.
- Роутер на ДБЖ, **білий (публічний) IP** або DDNS, можливість пробросити порт.
- VPS з Docker і Docker Compose.
- Ключ каналу Світлобота (`channel_key`).
- За бажанням — Telegram-бот, доданий адміністратором у ваш канал.

## Крок 1. Прошивка ESP32

### Встановлення утиліти

**Варіант А — готовий файл.** Завантажте з розділу Releases файл для своєї ОС (`svitlo-flasher-macos-arm64`, `svitlo-flasher-windows-x64.exe`, `svitlo-flasher-linux-x64` тощо). Прошивка вже вбудована всередину.

**Варіант Б — з вихідного коду** (потрібен Python ≥ 3.9):

```bash
pip install ./cli
```

```bash
python cli/scripts/build_firmware.py
```

Друга команда збирає прошивку (потрібен `pip install platformio`) і кладе образ у пакет. Після неї ще раз виконайте `pip install ./cli`.

> На Windows може знадобитися драйвер USB-UART: CP210x або CH340 — залежно від плати.
> На Linux додайте користувача до групи `dialout`: `sudo usermod -aG dialout $USER` (і перезайдіть).

### Прошивка

```bash
svitlo-flasher flash --ssid "НазваМережі" --key "довгий-випадковий-ключ"
```

Утиліта сама знайде порт (або вкажіть `--port COM3` / `--port /dev/ttyUSB0` / `--port /dev/cu.usbserial-0001`), запише прошивку, запитає пароль Wi-Fi, передасть налаштування й покаже IP-адресу ESP32.

Корисні параметри:

| Параметр | Опис |
|---|---|
| `--http-port 8080` | порт сторінки на ESP32 |
| `--key …` | ключ доступу до сторінки (рекомендовано, щоб відповідь не можна було підробити) |
| `--static-ip 192.168.1.50 --gateway 192.168.1.1 --subnet 255.255.255.0` | статичний IP замість DHCP |
| `--erase` | повністю стерти flash перед записом |

Інші команди:

```bash
svitlo-flasher ports
```

```bash
svitlo-flasher info
```

```bash
svitlo-flasher configure --ssid "ІншаМережа"
```

```bash
svitlo-flasher monitor
```

`configure` змінює налаштування без перепрошивки, `info` показує поточний стан, `monitor` — вивід ESP32, `reset-config` — стирає налаштування.

ESP32 підтримує лише Wi-Fi **2,4 ГГц**.

### Перевірка в локальній мережі

```bash
curl -H "X-Svitlo-Key: ваш-ключ" http://192.168.1.50:8080/status
```

Відповідь: `{"status":"ok","device":"svitlobot-esp32","version":"0.1.0","uptime_s":42,"rssi":-55,"message":"Світло є"}`.

## Крок 2. Налаштування роутера

1. Закріпіть за ESP32 постійну адресу (DHCP-резервування) або використайте `--static-ip`.
2. Пробросьте зовнішній TCP-порт (напр. `18080`) на `IP_ESP32:8080`.
3. Переконайтеся, що роутер відповідає на ICMP-пінг ззовні. Якщо ні — у налаштуваннях сервісу оберіть перевірку «TCP-з'єднання» з будь-яким портом роутера, який відповідає навіть без ESP32 (наприклад, інший проброшений порт або веб-інтерфейс роутера). Навіть закритий порт, що відповідає відмовою (RST), вважається ознакою «роутер живий».

## Крок 3. Сервіс на VPS

### Автоматичний деплой (GitHub Actions)

При кожному пуші в `main` workflow [`deploy.yml`](.github/workflows/deploy.yml) запускає тести, перевіряє збирання образу, а потім по SSH оновлює код у теці проєкту на сервері, створює там `.env` із секретів і перезбирає контейнер.

Підготовка сервера (один раз):

1. Встановіть Docker з Compose v2 і додайте користувача деплою до групи `docker`: `sudo usermod -aG docker <користувач>`.
2. Додайте публічну частину SSH-ключа в `~/.ssh/authorized_keys` цього користувача (ключ без пароля).

Секрети репозиторію (*Settings → Secrets and variables → Actions*):

| Секрет | Обов'язковий | Призначення |
|---|---|---|
| `HOST` | так | адреса сервера |
| `SSH_USER` | так | користувач SSH |
| `SSH_KEY` | так | приватний SSH-ключ |
| `PROJECT_FOLDER` | так | тека проєкту на сервері, напр. `~/Svitlobot` |
| `PANEL_USERNAME` | так | логін до веб-панелі |
| `PANEL_PASSWORD` | так | пароль до веб-панелі |
| `SVITLOBOT_TOKEN` | так | ключ каналу Світлобота (`channel_key`) |
| `TARGET_IP` | так | зовнішній IP або домен об'єкта |
| `TELEGRAM_BOT_TOKEN` | ні | токен Telegram-бота |
| `SVITLOBOT_CHANNEL` | ні | ID Telegram-каналу для повідомлень (`-100…` або `@назва`) |
| `SSH_PORT` | ні | порт SSH (типово 22) |
| `SSH_KNOWN_HOSTS` | ні, але рекомендовано | вивід `ssh-keyscan <HOST>` — перевірка ключа сервера |
| `ESP_PORT`, `ESP_KEY` | ні | зовнішній порт і ключ доступу ESP32 |
| `WEB_PORT`, `WEB_BIND` | ні | порт панелі та адреса прослуховування (напр. `127.0.0.1`) |

Як захищено секрети:

- в образ контейнера вони не потрапляють — `.env` лежить лише на сервері (права `600`) і монтується в контейнер тільки для читання; у змінних оточення контейнера їх теж немає;
- жоден крок workflow не виводить їх значень: секрети передаються в кроки через `env:`, файл формується скриптом, який друкує лише назви змінних, логи контейнера в Action не показуються;
- Docker Compose на сервері запускається з окремим `compose.env` (лише `WEB_PORT`/`WEB_BIND`), щоб він не розбирав `.env` і не вивів фрагмент секрету в попередженні.

Структура теки проєкту на сервері:

```
~/Svitlobot/
├── .env              # створює GitHub Action, перезаписується при кожному деплої
├── compose.env       # параметри для Docker Compose (без секретів)
├── docker-compose.yml, Dockerfile, app/ …
└── data/
    ├── .env.override # зміни з веб-панелі — мають пріоритет над .env, деплой їх не чіпає
    └── state.json    # стан і журнал подій
```

### Ручний запуск

```bash
cd server
cp .env.example .env
nano .env
docker compose up -d --build
```

### Веб-панель

Відкрийте `http://IP_VPS:8080` і увійдіть з `PANEL_USERNAME` / `PANEL_PASSWORD`.

- Біля кожного поля видно, звідки взято значення: мітка `.env` — із файлу, `панель ↺` — змінено в панелі. Натискання на `панель ↺` повертає значення з `.env`; кнопка «Скинути всі зміни панелі» прибирає всі перевизначення.
- Зміни з панелі пишуться в `data/.env.override`, а не в `.env`, тож наступний деплой їх не затре. Якщо значення в панелі збігається з `.env`, перевизначення прибирається автоматично.
- Кнопка **«Перевірити все»** перевіряє налаштування без побічних ефектів: доступність сторінки ESP32 і ключа доступу, пінг/TCP до IP, токен бота (`getMe`), доступ бота до каналу та право публікації. Ключ Світлобота перевіряється тестовим пінгом лише тоді, коли сервіс і так зараз пінгує (світло є); інакше доступна окрема кнопка, бо пінг позначив би в каналі «світло є».
- Логін і пароль панелі змінюються тільки через `.env` (секрети репозиторію).

### Поведінка у стані «невідомо»

| Варіант | Що відбувається |
|---|---|
| Зберігати останній відомий стан *(типово)* | якщо до втрати зв'язку світло було — пінги тривають, Світлобот не показує хибного відключення |
| Вважати, що світло є | пінги тривають завжди |
| Зупинити пінги | Світлобот покаже відключення (як у класичній схемі) |

### Повідомлення в Telegram

Повідомлення оформлені так само, як у Світлобота, але з іншими емодзі, і надсилаються тихо (`disable_notification`):

```
📵 05:26 Зник інтернет
⏳ Статус світла тимчасово невідомий

📶 07:48 Інтернет з'явився
⏳ Його не було 2год 22хв
```

Час — момент першої невдалої (або першої успішної) перевірки, а не момент підтвердження. Тексти можна змінити у веб-інтерфейсі; доступні змінні `{time}`, `{date}`, `{duration}`, `{status}`, `{last_status}`.

Про зміни самого світла пише Світлобот, тож наш бот їх не дублює.

### Безпека

- Веб-панель захищена HTTP Basic Auth. Пароль передається відкрито, тому рекомендовано або поставити реверс-проксі з HTTPS (Caddy, nginx), або задати `WEB_BIND=127.0.0.1` і заходити через SSH-тунель:

  ```bash
  ssh -L 8080:127.0.0.1:8080 user@ваш-vps
  ```

- Секрети (токени, ключі) не повертаються у веб-інтерфейс після збереження.

### Оновлення

Пуш у `main` — і GitHub Action розгорне нову версію. Вручну — workflow «Деплой» → *Run workflow*.
